# Agent Note: Electron desktop starts as a replaceable loopback Web supervisor

Status: implemented

English | [中文](2026-08-14-electron-loopback-web-supervisor.zh.md)

## Problem

The desktop application needs an Electron window and a tray-owned application lifetime without making the window the owner of Harness work. Closing the window must leave sessions and background work running, while an explicit application quit must dispose the Harness process and wait for its descendants. Building the final Electron IPC carrier at the same time would also require a packaged client-module loader, an IPC streaming transport, native-operation routing, and a new renderer security boundary before the first usable shell could ship.

The existing Web profile already provides the complete interactive client, ApiProxy validation, session replay, approval handling, configuration UI, and native Host operations. The first desktop implementation needs to reuse those behaviors without making its process arrangement permanent or weakening the [channel-independent GUI protocol](2026-07-19-gui-layering-and-rpc-protocol.md).

## Decision

`@deepseek-ai/dsh-desktop` in `apps/desktop` is a private Electron application and a replaceable supervisor, not a new Harness composition or protocol carrier. It starts one `dsh --profile web` child bound to loopback on an operating-system-assigned port, then loads the canonical URL from the child's `dsh web: <url>` readiness line. The readiness parser follows stream chunks rather than stdout callback boundaries, ignores unrelated output and the optional LAN annotation, and accepts only an HTTP loopback authority with a valid nonzero port. A malformed readiness line, startup error, early child exit, or end-of-stream before readiness fails startup instead of navigating to an inferred address.

The root `dev:desktop` command is the complete source-launch entry. Before Electron starts, it builds the Host and client package faces, the Web frontend, and the Electron main process, so a fresh dependency installation does not require a separate repository build.

The root `package:desktop` command is the complete local packaging entry. It performs the same repository build, then `apps/desktop/scripts/stage-runtime.ts` creates an ignored `apps/desktop/runtime-host` tree from a dependency-only manifest. The stager runs a production-only hoisted `pnpm deploy`, restores direct dependencies omitted by legacy deploy, materializes package links, removes TypeScript declarations and source maps that Node never loads, and rejects every remaining symbolic link. Electron Builder copies that closed tree into the application's `resources/host` directory together with the built Web frontend.

The packaged supervisor starts `resources/host/node_modules/@deepseek-ai/dsh/lib/bin.js` with the packaged Electron executable and `ELECTRON_RUN_AS_NODE=1`; source launches continue to use the host `node` command and workspace CLI entry. Electron's Node mode provides the separate Host process without adding a second Node executable to the application. The shipped Electron Node ABI therefore owns compatibility with native dependencies in the staged closure.

macOS and Windows use the same tracked `apps/desktop/build/icon.png` input without repository-side conversion. Local `package:desktop` output is unpacked and does not require distribution credentials. The separate `dist:mac:desktop` entry enables hardened runtime, forces signing, and requires a complete Electron Builder notarization credential group before it creates a DMG. Signing accepts either a persistent Keychain identity containing a `Developer ID Application` certificate and private key or a Base64 PKCS#12 credential that Electron Builder imports into its temporary Keychain. The release wrapper withholds signing and notarization variables from repository build and runtime staging, then exposes them only to Electron Builder. The preflight rejects non-macOS hosts, disabled identity discovery, a non-Developer-ID identity, and missing or partial credentials before running the repository build. A `notarytool` Keychain profile or complete Apple ID or App Store Connect API key group supplies notarization credentials.

The root `dist:win:desktop` entry builds a guided Windows x64 NSIS installer. The assisted flow defaults to the current user, offers an all-users mode, and lets the user choose the installation directory. Runtime staging explicitly targets `win32-x64`, and the pre-pack gate requires the Windows Koffi, Sharp, node-addon loader, and node-pty binaries in addition to the ordinary Host and Web entrypoints. Electron Builder resolves the target-platform Electron distribution instead of reusing the build host's installed Electron. On macOS, the release wrapper exposes app-builder-lib's NSIS templates through a short temporary symlink because NSIS's POSIX `__FILEDIR__` implementation still uses a fixed 260-character buffer; the symlink is removed after Builder exits. Before replacement or removal, NSIS launches the installed executable with the private `--dsh-installer-quit` argument, allows five seconds for ordered Host disposal, then makes two bounded exact-name process-tree termination attempts. A surviving process fails the operation explicitly instead of allowing partial removal. Every registered `0.1.0-rc.*` preview installation has an additional same-directory replacement path: when the registered location is the dedicated product directory, the replacement installer removes the previous application and its two uninstall command values, then lets the normal install section recreate the payload and complete uninstall registration without invoking an older preview uninstaller. The application directory contains no Profile data. Internal Windows test packages remain unsigned until an Authenticode certificate is configured.

`.github/workflows/desktop-release.yml` is the GitHub installer publication path. It accepts only an immutable `desktop-v<version>` tag that exactly matches `apps/desktop/package.json`, then builds a signed and notarized macOS arm64 DMG plus updater ZIP and an Authenticode-signed Windows x64 NSIS installer on native hosted runners. Each platform verifies its signature before uploading a short-lived workflow artifact. The final job requires both platforms, generates `SHA256SUMS`, creates a draft GitHub Release with every asset, and makes it public only after the complete upload succeeds. The repository README links the Releases page before the first installer exists without presenting source archives or unpacked applications as downloads. The dispatch-only Windows installer lifecycle workflow builds an unsigned branch artifact without modifying a Release, installs it into a non-default directory, starts the packaged Host, uninstalls it while running, reinstalls it into the same directory, and repeats the launch and uninstall check.

The child remains the sole owner of the Web profile's Cordis tree, sessions, settings, credentials, filesystem and shell services, HTTP/WebSocket carrier, and quiescent disposal. Electron does not import those services into its main or renderer process. The BrowserWindow loads the validated loopback URL with Node integration disabled, context isolation and renderer sandboxing enabled, and no preload capability. This is still the existing local Web security model: the desktop shell adds no authentication or IPC authorization layer.

The tray and Host supervisor own application lifetime independently of BrowserWindow visibility. A user window close is intercepted and hides the window; it neither quits Electron nor signals the child. Tray activation and macOS application activation show the existing window again. `window-all-closed` is not an exit request. The single-instance lock prevents a second desktop process and second Host child. An ordinary second launch restores and focuses the primary window; the exact private Windows installer argument instead enters the same explicit-quit operation used by the tray.

Every explicit exit path converges on one idempotent quit operation. It stops accepting window-restoration work, sends `SIGTERM` to the child, and waits for the child to exit. The ordinary `dsh` launcher handles that signal by disposing the root Cordis fiber, whose owned persistence and subprocess services drain before process exit. A bounded timeout escalates an unresponsive child to `SIGKILL` once and still waits for child settlement before Electron exits. Repeated quit requests join the same operation rather than starting another signal or timer sequence.

An unexpected child exit after readiness reports its exact code and signal, then enters the same application quit operation. The shell does not leave a live window attached to a dead Host and does not restart an execution environment without an explicit recovery policy.

The supervisor presents start/readiness/shutdown facts to the Electron application instead of exposing child-process mechanics to window and tray handlers. A later local custom-protocol plus IPC carrier may replace the loopback child behind this ownership point. That migration replaces asset loading and transport while retaining the tray/window lifetime rules and the existing ApiProxy message model; the first phase does not introduce a compatibility promise for the child arrangement.

### Desktop chrome

BrowserWindow chrome is platform-specific. macOS uses a frameless inset hidden title bar, sidebar vibrancy, and an explicit traffic-light position; its collapsed sidebar resolves to a 90px rail whose 36px controls are centered, and the top control aligns with the expanded logo row below the traffic lights. Windows keeps a standard thick frame and shadow for resize, Snap, and Windows 11 rounded corners, then extends content through a hidden title bar with native caption controls and acrylic material. Linux remains frameless and keeps the Web client's opaque surfaces because Electron provides no equivalent native material there. The window remains hidden until the renderer is loaded with its desktop presentation marker.

Electron appends one allowlisted platform value to the validated Host URL. The Web entry consumes it before mounting the client tree, marks the root element as a desktop document, and records the platform. This static marker grants no preload or IPC capability. Client styles use it only for native presentation and title-bar hit regions. The resident conversation root always mounts a center-column drag band, including when no Session header is visible. A visible macOS header is draggable; Windows instead composes its 44px first row with the native caption controls, reserves their right-side area, and keeps only the row's non-interactive area draggable. Buttons, links, form fields, ARIA controls, tabs, and editable descendants are explicit no-drag regions so window movement does not consume their interaction. While any `aria-modal="true"` dialog is mounted, the document makes every renderer-owned drag target `no-drag`, including background title bars and modal overlays; removing the final modal restores the platform rules. macOS and Linux own separate sidebar drag strips; Windows has no traffic-light inset or sidebar drag strip.

Native material is admitted only through the sidebar on macOS and Windows: the page and AppFrame backgrounds become transparent, the sidebar paints a theme-derived translucent tint, and the conversation and details columns repaint the ordinary opaque application background. The Session list suppresses its opaque bottom overflow fade on those native-glass sidebars so the tint does not darken at the list edge. Browser-served clients have no desktop marker and retain their existing layout and colors. This keeps platform chrome a carrier-specific presentation choice rather than a new client capability or protocol field.

## Alternatives considered

**Build the IPC carrier before shipping any desktop application.** This is the target transport direction, but it combines process security, client-module packaging, bidirectional streaming, cancellation, native operations, and lifecycle work in one first release. The supervisor keeps that migration available without making all of it a prerequisite for a tray shell.

**Boot the Harness plugin tree inside Electron's main process.** This removes one child process and the loopback socket, but it couples model, persistence, and subprocess failures to the process that must keep the tray and quit controls responsive. It also creates a second application assembly instead of exercising the shipped Web profile.

**Terminate the child whenever the window closes.** This makes BrowserWindow visibility own agent lifetime, discards background work, and contradicts a tray-resident application. Only an explicit application quit owns Host disposal.

**Destroy and recreate the BrowserWindow on close.** Session replay can reconstruct durable conversation state, but transient client state and open controls would be lost. Hiding preserves the current client generation for the first shell; accepting its renderer memory cost is explicit.

**Use a fixed loopback port or infer the address from process arguments.** A fixed port creates avoidable collisions and an inferred URL can race a server that has not completed Loader activation. Port zero plus the existing post-settlement readiness line lets the child report the address it actually owns.

**Kill the child immediately on explicit quit.** Immediate termination shortens shutdown but skips session flushes and managed process-tree cleanup. `SIGTERM` delegates disposal to the child; forced termination remains only the bounded failure path.

**Rely only on Electron Builder's generic running-process check during Windows replacement.** That check cannot ask the tray-owned application to drain its Host and has failed to release the installed tree for a downloaded package. The installer first invokes the application's owned quit path, then replaces the generic prompt loop with exact process-tree termination for older or unresponsive versions.

**Keep the native title bar and an opaque sidebar.** This avoids carrier-specific styling, but gives the desktop application browser-like chrome and cannot use the platform material already owned by its native window. The desktop marker confines the required layout adjustment to Electron instead.

**Make the whole workspace translucent.** Extending native material behind conversation and details content would reduce text contrast and make theme surfaces depend on the desktop beneath the window. Only the navigation sidebar admits material; working content remains opaque.

**Upload local installer files directly to a public Release.** A local working tree can include uncommitted code, stale runtime staging, the wrong architecture, or incomplete signing. Tag-owned native builds and an unpublished draft keep source identity, platform verification, checksums, and all-or-nothing publication in one repeatable path.

## Consequences

The desktop application ships the existing interactive product with little Host or client risk, and closing its window leaves the agent runtime available from the tray. The extra process also isolates Electron's application controls from ordinary Harness failures and leaves one explicit point where the transport can later change.

This phase pays for a loopback listener, an additional Node process, readiness-line coupling, and the resource cost of a hidden renderer. It inherits the Web carrier's trust and exposure rules rather than gaining an Electron IPC security boundary. Custom chrome makes the client responsible for platform-specific title-bar clearance, usable drag targets, and no-drag interaction regions; Linux remains frameless without a native glass material, while Windows depends on Window Controls Overlay geometry. A distributable package carries the CLI production dependency closure and Web frontend, while Electron's Node mode avoids a duplicate Node binary at the cost of coupling native dependency compatibility to Electron's shipped ABI. Runtime staging also depends on legacy `pnpm deploy` behavior and therefore restores omitted direct dependencies and removes links before Builder consumes the tree. Formal macOS distribution requires an external Developer ID identity, notarization credentials, and Apple's notarization service; formal Windows distribution still requires an Authenticode identity, while Linux installer format and signing remain separate release work. Desktop startup succeeds only after the child reports its post-Loader URL. A Host crash exits the shell instead of recovering the current window; automatic restart remains a later lifecycle decision.

GitHub publication additionally requires the `desktop-release` environment, the macOS and Windows signing secrets, and an exact version tag. This delays public downloads until both platform identities are configured, but a failed platform build cannot leave users with a partial or source-mismatched Release. Windows replacement or removal can add up to seven seconds when an installed process is detected; this bound buys ordered Host disposal and two forced cleanup attempts for already-distributed or unresponsive versions. Removing compile-time metadata reduces installer extraction work but also removes packaged source-level debugging maps and declarations that the runtime does not consume.

The child arrangement is an implementation choice, not a public protocol. A future IPC-backed desktop still uses the four-quadrant ApiProxy contract and preserves close-as-hide, tray ownership, single-instance behavior, and ordered Host disposal, while replacing the loopback server, readiness line, and supervised CLI process.
